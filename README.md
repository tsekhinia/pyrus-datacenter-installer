# Pyrus Datacenter Installer

## Выгрузить диагностику одной командой

На сервере с уже установленным Pyrus, из папки, куда нужно сохранить ZIP:

```bash
wget -O pyrus-collect-logs.sh https://raw.githubusercontent.com/tsekhinia/pyrus-datacenter-installer/main/collect-logs.sh && sudo bash pyrus-collect-logs.sh
```

Результат — `pyrus-diagnostics-ИМЯ_СЕРВЕРА-ДАТА-ВРЕМЯ-ID.zip` **в папке запуска**.
Сборщик работает отдельно от установщика: достаточно `bash`, `python3`, Docker CLI,
`df` и `free`. Утилита `zip`, образ `pyrus-setup`, каталог `.installer` не нужны.
Для V2 вызывается `docker compose`, для установленного V1 — `docker-compose`.

В архив попадают:

- `df.txt` — `df -h`;
- `free.txt` — `free -h`;
- `docker_stats.txt` — `docker stats --no-stream`;
- `docker_compose_ps.txt` — `docker compose ps -a` (или V1) выбранного проекта;
- `errors.txt` и `warnings.txt` — все строки `events.errors_YYYY_MM_DD` и
  `events.warnings_YYYY_MM_DD` из `pyrus_logs` от имени `pyrusadm`;
- `database_time.txt`, список контейнеров, `report.txt` и непустой stderr команд.

Пустые файлы `*.stderr.txt` в архив не добавляются. Сообщения в stderr
сохраняются и при успешном завершении команды, например предупреждения утилит.

По умолчанию выгружаются таблицы за **сегодня по дате PostgreSQL**; дата, время
и часовой пояс БД сохраняются в архиве. Файлы читаются потоком, без накопления
суточных логов в оперативной памяти. На сервере требуется свободное место
для временной текстовой выгрузки и итогового ZIP. После упаковки временные файлы удаляются.

Если команда Compose не работает из текущей папки (например, рядом нет YAML),
дополнительно сохраняется `docker_compose_ps_fallback.txt`: `docker ps -a`
с фильтром по Compose-проекту. Причина отказа исходной команды остаётся в stderr.
Показатели диска, RAM и `docker stats` относятся ко всему серверу, как в ручном сборе.

Ошибки отдельных команд не прерывают сбор остальных данных. Если контейнер
остановлен, таблица отсутствует, нет доступа к Docker или сработал таймаут,
ZIP всё равно создаётся с пометкой «СОБРАНО ЧАСТИЧНО» в `report.txt`.
Пустая существующая таблица — успешная выгрузка с `(0 rows)`.
Коды завершения: `0` — всё собрано; `2` — частичный архив или неверные аргументы;
`1` — создать архив не удалось. Путь к созданному архиву печатается в терминале.

Дополнительные варианты после скачивания:

```bash
# Другая дата:
sudo bash pyrus-collect-logs.sh --date 2025-07-10

# Явный контейнер или выбор проекта, если установок несколько:
sudo bash pyrus-collect-logs.sh --container pyrus-logs-pgsql
sudo bash pyrus-collect-logs.sh --project ubuntu

# Таймаут каждой команды (по умолчанию 180 секунд):
sudo bash pyrus-collect-logs.sh --timeout 600

# Из полного репозитория (сначала --logs, затем его параметры):
sudo bash install.sh --logs
sudo bash install.sh --logs --date 2025-07-10
```

Контейнер БД определяется по имени `pyrus-logs-pgsql` или сервису `logs` в
проекте с контейнерами Pyrus. При неоднозначности сборщик пишет в отчёт список
кандидатов и просит явно указать проект или контейнер; чужая БД не выбирается.
SQL запускается без TTY, без пароля в аргументах, с отключённым `.psqlrc`,
в режиме только чтения и с таймаутами запроса/блокировки. Файлы в контейнере
не создаются. Контейнеры не перезапускаются, параметры установки не меняются.

Архив содержит исходные логи без маскирования; в них могут быть персональные
данные и секреты. Права ZIP — `0600`; при `sudo` владельцем становится запускающий
пользователь. Передавайте архив поддержке по принятому защищённому каналу.

Экспериментальный установщик **Pyrus Datacenter 1.27.0** на новый сервер
**Ubuntu 22.04 / 24.04, amd64, Docker Compose V2**. Код подготовлен для пробной
установки на отдельную VM. Полный запуск лицензированного Pyrus ещё не проверен.
Это самостоятельная автоматизация официальной инструкции, не официальный
продукт Pyrus.

## 1. Что подготовить

Следующие требования относятся к новой установке. Для просмотра и изменения
параметров ранее установленного Pyrus используйте `--menu` из раздела 3:
обновлять Docker или устанавливать плагин Compose для этого режима не требуется.

- Новый сервер без существующих контейнеров, сетей и томов Pyrus.
- Docker Engine 24+ и плагин `docker compose` 2.24+. Docker daemon должен быть
  локальным, с Unix socket. Установщик не устанавливает Docker и не меняет его
  настройки. [Инструкция Docker для Ubuntu](https://docs.docker.com/engine/install/ubuntu/).
- Ориентир на 100 пользователей: 8 CPU, 32 GB RAM, 300 GB SSD. Меньшие ресурсы
  допускаются только для теста с `--accept-low-resources`; работоспособность
  и скорость при этом не гарантированы.
- DNS-имя, направленное на сервер или его NAT. Сервер и рабочие станции должны
  разрешать это имя. Установщик не меняет DNS.
- PEM-сертификат с полной цепочкой и соответствующий незашифрованный PEM-ключ.
  Для внутреннего УЦ потребуется CA bundle и доверие на рабочих станциях.
- Лицензия Pyrus, email и пароль первого администратора.
- SMTP: сервер, порт, режим SSL, учётные данные при необходимости и адреса
  отправителя уведомлений / восстановления пароля. Соответствие SSL/STARTTLS
  уточните у администратора почты; скрипт передаёт документированный
  параметр Pyrus `SMTP_USE_SSL` без самостоятельной интерпретации режимов.
- TCP 80 и 443 свободны на сервере, входящий 443 доступен рабочим станциям.
  Исходящий HTTPS к `pyrus.com`, `dc.pyrus.com`, `cr.yandex` и адресам, куда
  registry перенаправляет загрузку образов; доступ к SMTP и при необходимости S3.

На сервере также нужны стандартные утилиты Ubuntu:

```bash
sudo apt-get update
sudo apt-get install -y curl openssl python3 iproute2 util-linux coreutils procps ca-certificates wget
docker version
docker compose version
```

## 2. Запуск

### Одной командой

В терминале сервера Ubuntu выполните:

```bash
wget -O pyrus-bootstrap.sh https://raw.githubusercontent.com/tsekhinia/pyrus-datacenter-installer/main/bootstrap.sh && sudo bash pyrus-bootstrap.sh
```

Если работаете под root, `sudo` можно опустить. Запустится интерактивный мастер:
он соберёт параметры, покажет план и запросит `yes` перед установкой.
Docker, Compose и остальные зависимости из раздела 1 должны быть установлены.

Вариант с `curl`:

```bash
curl -fSL https://raw.githubusercontent.com/tsekhinia/pyrus-datacenter-installer/main/bootstrap.sh -o pyrus-bootstrap.sh && sudo bash pyrus-bootstrap.sh
```

Git, SSH-ключ и авторизация GitHub не нужны: репозиторий публичный. Загрузчик
скачивает полный комплект модулей по HTTPS, сверяет SHA-256 архива и запускает
`install.sh`. Закреплён коммит `7fed725ed7b0785fbb106a793ebeabc22ba83d2e` с поддержкой существующих установок;
новый код из `main` сам по себе не меняет скачиваемую версию установщика.
Временный комплект удаляется после завершения; состояние Pyrus остаётся в
каталоге установки. Все параметры передаются основному скрипту:

```bash
# Проверки сервера без установки:
sudo bash pyrus-bootstrap.sh --preflight

# На небольшой тестовой VM:
sudo bash pyrus-bootstrap.sh --accept-low-resources

# Продолжить после ошибки или проверить установленный Pyrus:
sudo bash pyrus-bootstrap.sh --resume
sudo bash pyrus-bootstrap.sh --check
sudo bash pyrus-bootstrap.sh --menu
```

В интерактивном терминале поддерживается и запуск без сохранения загрузчика:

```bash
wget -qO- https://raw.githubusercontent.com/tsekhinia/pyrus-datacenter-installer/main/bootstrap.sh | sudo bash
```

Для параметров при таком запуске используйте `sudo bash -s -- --preflight`
или `sudo bash -s -- --resume`. Загрузчик подключает ввод мастера к терминалу,
чтобы работали скрытый ввод паролей и подтверждение `yes`. Основной вариант
с `wget -O … && sudo bash …` сначала полностью скачивает загрузчик и проверяет
успех скачивания.

### Запуск из исходников

Для просмотра кода, работы с JSON-шаблоном или разработки можно скачать
репозиторий отдельно (в этом случае нужен Git):

```bash
git clone https://github.com/tsekhinia/pyrus-datacenter-installer.git
cd pyrus-datacenter-installer
sudo bash install.sh --preflight
sudo bash install.sh
```

Для повторного использования параметров подготовьте JSON вместо мастера:

```bash
sudo install -m 600 templates/installer.json.example /root/pyrus-install.json
sudo nano /root/pyrus-install.json

# Только проверить параметры, TLS, сервер и показать план. Установка не начинается.
sudo bash install.sh --config /root/pyrus-install.json --plan

# Выполнить установку; потребуется подтверждение yes в терминале.
sudo bash install.sh --config /root/pyrus-install.json
```

Пример для тестового сервера с меньшими ресурсами:

```bash
sudo bash install.sh --accept-low-resources
```

По умолчанию установка идёт в `/opt/pyrus`. Другой путь передавайте через
`--install-dir /srv/pyrus` при установке, продолжении и проверке.
Конфигурационный JSON должен принадлежать запускающему пользователю (при
`sudo` — root) и иметь права `0600`. Не передавайте секреты через командную строку
и не добавляйте заполненный JSON в Git.

## 3. Просмотр и изменение конфигурации

Для ранее установленного Pyrus или завершённой установки этим скриптом откройте
интерактивное меню:

```bash
sudo bash pyrus-bootstrap.sh --menu
# Из скачанного репозитория:
sudo bash install.sh --menu
# Если установка находится в другом каталоге:
sudo bash install.sh --menu --install-dir /srv/pyrus
```

Без сохранения загрузчика вручную:

```bash
wget -qO- https://raw.githubusercontent.com/tsekhinia/pyrus-datacenter-installer/main/bootstrap.sh | sudo bash -s -- --menu
```

Если каталога `.installer` нет, меню обнаруживает существующие контейнеры Pyrus
по меткам Compose. Оно работает и с установками, созданными старой командой
`docker-compose`: в этом режиме используется только Docker CLI, команды Compose
не вызываются. При наличии нескольких проектов выбирается нужный. Можно указать
его явно: `--menu --project ИМЯ_ПРОЕКТА`.

Поддерживается стандартная установка с работающими `web-api` и `postgres` в одном
Compose-проекте и одной общей Docker-сети. Меню использует локальный образ
`pyrus-setup` того же тега версии, что и работающий `pyrus-web-api`, и закрепляет
его локальный ID. Если реестр отличается, укажите уже имеющийся локальный образ
параметром `--setup-image registry/pyrus-setup:ВЕРСИЯ`. Известные теги версии
проверяются на совпадение. Недостающие образы автоматически не скачиваются.

Подключения к БД берутся из окружения работающего `web-api` и передаются
временному контейнеру `pyrus-setup` через окружение процесса. Пароли не записываются
в файлы и не передаются аргументами Docker. Исходные Compose-файлы не читаются
и не изменяются; файлы `.env`, каталог `.installer` и повторная установка не нужны.
Временный контейнер удаляется после команды; зависимости не запускаются.
Перезапуск затрагивает только уже работающие известные сервисы приложения.

Повторный запуск без указания режима также открывает меню существующей
установки. Для незавершённой установки используйте `--resume`.

В меню доступны:

1. Основные параметры: домен, SMTP и генератор превью. Значения читаются из
   работающего Pyrus; лицензия и пароль SMTP скрыты.
2. Просмотр отдельного параметра по числовому ID.
3. Изменение параметра по ID: новое значение, проверка и подтверждение `yes`.
   Например, ID `101301` — SMTP-сервер, `101302` — порт, `101503` — пароль SMTP.
4. Полная конфигурация. Этот вывод включает секреты и показывается только
   после отдельного подтверждения `yes`.
5. Перезапуск сервисов приложения после отдельного подтверждения. PostgreSQL,
   Elasticsearch, NATS и MinIO не перезапускаются. Pyrus временно недоступен.
0. Выход.

Команды чтения и записи соответствуют [справке Pyrus](https://pyrus.com/ru/help/datacenter/parameters):
`--setup -ls`, `--setup -ls -id ID`, `--setup -id ID -v VALUE`.
Неизвестные ID также поддерживаются и считаются секретными: их просмотр
требует подтверждения, ввод при изменении скрыт и повторяется дважды.
Enter вместо нового значения отменяет изменение; удаление/очистка параметров
через это меню не поддерживается. Пустое или неверное значение не записывается.

Меню работает в терминале. Для установки, завершённой этим скриптом, сохраняются
проверки Compose и идентичности БД. Для существующей установки проверяются
контейнеры, их общая сеть и локальный образ; перед каждой командой проверяется,
что выбранные контейнеры не были заменены или остановлены. Вывод команд управления не попадает в
журналы установщика; новые секреты не сохраняются в его JSON. Подтверждённый
просмотр секретов остаётся видимым в терминале — учитывайте запись сессии.
Как и при установке, Pyrus CLI получает значение аргументом процесса Docker;
root и администраторы Docker могут его видеть.

После успешной записи домена или открытых SMTP-параметров обновляется снимок
установщика, если он имеется, чтобы `--check` использовал актуальные значения.
Новый домен должен покрываться установленным TLS-сертификатом; DNS настройте заранее.
Для ранее установленного Pyrus сертификат ищется в стандартном bind-mount nginx.
Если он не найден, остальные параметры доступны, а для изменения домена нужно
передать `--menu --tls-cert /path/fullchain.pem`.
Настройка домена не заменяет сертификаты. Обновление параметров S3 по ID
не переносит существующие файлы между хранилищами. Меню не меняет версию Pyrus,
пароли PostgreSQL/MinIO, TLS-файлы и учётную запись администратора.

При ошибке команды меню остаётся открытым. Перед повтором записи проверьте
текущее значение: команда могла примениться частично. После изменения параметров
может потребоваться пункт 5, затем `--check` и проверка входа, почты и вложений.
На установке этого скрипта отметка о рекомендуемом перезапуске сохраняется между
запусками меню. Для существующей установки отметка действует только в текущем
сеансе, служебный каталог установщика не создаётся. `--check` по-прежнему
предназначен для установок, завершённых этим скриптом; для старой установки
проверьте `docker ps`, вход в Pyrus и доставку почты.

## 4. Что делает скрипт

1. Проверяет ОС, архитектуру, ядро, ресурсы, локальный Docker, версии, порты,
   сетевые подключения и отсутствие существующих ресурсов Pyrus.
2. Собирает параметры, проверяет hostname, email, сертификат, ключ и SMTP TCP.
3. Показывает план. Только после `yes` создаёт каталог установки.
4. Генерирует пароли PostgreSQL и MinIO, копирует TLS-файлы в закрытый каталог.
5. Если `vm.max_map_count` меньше 262144, записывает постоянную настройку
   `/etc/sysctl.d/99-pyrus-installer.conf` и применяет только этот файл.
6. Скачивает официальный Compose, проверяет известный SHA-256, преобразует его
   средствами настоящего Compose V2 и сохраняет рабочий файл.
7. Задаёт одинаковый сгенерированный пароль в обеих БД и во всех строках
   подключения. Подключением по TCP проверяет доступ к обеим БД.
8. Скачивает только используемые образы и закрепляет их digest. При продолжении
   установки новая версия Pyrus не подхватывается.
9. Запускает PostgreSQL, БД логов, Elasticsearch, NATS. Дожидается готовности.
10. Выполняет официальные `--create --skip --setadmin`, `-ct --start`, `-iall`.
11. Настраивает MinIO / внешний S3, лицензию, домен и SMTP.
12. Запускает приложение, проверяет состояния контейнеров, наличие таблиц,
    идентичность БД и локальный HTTPS с проверкой сертификата.

Рабочий `docker-compose.yml` записывается в формате JSON, который является
валидным YAML и поддерживается Docker Compose. В нём остаются официальные
образы, healthcheck и зависимости. Госключ и ClickHouse вынесены в неактивный
профиль; `pyrus-setup` запускается с `--no-deps`, без случайного старта ClickHouse.

**После установки обязательно проверьте с рабочей станции:** вход в Pyrus,
доставку кода / уведомления по почте, загрузку и скачивание вложения. Проверка
SMTP TCP не проверяет пароль и доставку. Для внешнего S3 результат команды
настройки не заменяет проверку реального вложения.

## 5. Продолжение после ошибки

```bash
sudo bash install.sh --resume
# На маленькой тестовой VM:
sudo bash install.sh --resume --accept-low-resources
```

Сохраняются параметры и отметки выполненных этапов. Пароли не генерируются
заново. Проверяется SHA-256 рабочего Compose и идентичность обеих БД
(`system_identifier` и OID базы), чтобы не применить отметки старой установки
к новым томам. Это не проверка полной целостности данных.

Если оборвалась потенциально неповторяемая команда инициализации БД, индексов
или S3, автоматический повтор блокируется. Сначала изучите закрытый журнал и
состояние Pyrus. Когда повтор команды признан допустимым:

```bash
sudo bash install.sh --resume --retry-step db_init
# Другие допустимые этапы: db_start, elastic_init, storage.
```

`--retry-step` означает осознанный повтор конкретной команды и не исправляет
частично созданную схему. При сомнительном результате первой пробной установки
проще использовать новую пустую VM, сохранив старую для диагностики.
Скрипт не удаляет контейнеры, тома или БД и не выполняет `down -v`.

Уже завершённая установка при `--resume` только проверяется. Повторной
инициализации, изменения SMTP и скачивания образов не происходит.

## 6. Проверка и диагностика

```bash
sudo bash install.sh --check
sudo ls -lt /opt/pyrus/.installer/*.log
sudo tail -n 100 /opt/pyrus/.installer/install-YYYYMMDDTHHMMSSZ.log
```

Логи команд имеют права `0600`; известные секреты фильтруются. Не публикуйте
логи целиком без просмотра: ответы сторонних программ могут включать иные
конфиденциальные данные. Пароль администратора удаляется из состояния после
успешной инициализации БД; лицензия, SMTP и внешние S3-ключи удаляются из
состояния установщика по окончании установки. Pyrus хранит свою конфигурацию
в БД; пароль БД и MinIO также нужны рабочему Compose.

Для ручной диагностики используйте те же имя проекта, каталог и env-файл:

```bash
sudo docker compose --project-name pyrus --project-directory /opt/pyrus \
  --env-file /opt/pyrus/.installer/compose.env \
  -f /opt/pyrus/docker-compose.yml ps

sudo docker compose --project-name pyrus --project-directory /opt/pyrus \
  --env-file /opt/pyrus/.installer/compose.env \
  -f /opt/pyrus/docker-compose.yml logs --tail 100 web-api nginx
```

Доступ к Docker даёт доступ к секретам контейнеров. Документированный CLI Pyrus
принимает часть секретов аргументами, поэтому во время настройки их могут
увидеть привилегированные локальные процессы. Выполняйте установку на
контролируемом сервере. Удалите заполненный `/root/pyrus-install.json`, когда он
больше не нужен. Каталог установки и `.installer` храните с правами `0700`.

## Внешний S3

В мастере выберите `external`. Для JSON задайте дополнительно:

```json
{
  "STORAGE_TYPE": "external",
  "S3_ENDPOINT": "https://storage.yandexcloud.net",
  "S3_BUCKET": "your-bucket",
  "S3_ACCESS_KEY": "your-access-key",
  "S3_SECRET_KEY": "your-secret-key",
  "S3_STORAGE_TYPE": "Yandex",
  "S3_FORCE_PATH_STYLE": "true"
}
```

Это дополнение к основному шаблону, не отдельный полный конфиг. Документированные
типы: `MinIo`, `Mts`, `VkCloud`, `Yandex`. Endpoint должен быть доступен из
Docker-сети; `localhost` внутри контейнера не означает хост. Установщик не
создаёт облачную учётную запись и IAM-политику. Для нестандартного S3-совместимого
провайдера совместимость отдельно не подтверждена.

## Версия и официальный Compose

Проверенный источник: `https://pyrus.com/datacenter/1.27.0/docker-compose.yml`,
получен 20.10.2026, Pyrus 1.27.0.

```text
c2183ea98e4a6341ae5b492df32677190a71e6ac75eaa8a58d06ac1bfc37fb1d
```

Используется ссылка конкретного релиза, а не latest. Если Pyrus изменит файл,
скрипт остановится до запуска
контейнеров. Не заменяйте hash вслепую: нужно проверить новый Compose, образы,
зависимости, параметры и тесты. Автоматического обхода проверки hash нет.
Снимки в `tests/fixtures` предназначены для тестов,
установщик не читает их при реальном запуске.

Рабочий Compose после установки нельзя обновлять скачиванием latest-файла.
Обновление Pyrus, backup, восстановление, Cloud → DC, Kubernetes/HA и управление
уже существующей установкой в эту версию не входят. Продление сертификата:
скрипт использует копии в `.installer`; после замены копий сертификата/ключа
пересоздайте nginx и повторите `--check`.

## Разработка и проверки

```bash
for script in install.sh bootstrap.sh lib/*.sh; do bash -n "$script"; done
shellcheck -x install.sh bootstrap.sh lib/*.sh
python3 -m py_compile scripts/*.py tests/*.py
python3 -m unittest discover -s tests -v

# Для дополнительной проверки настоящим парсером Compose:
COMPOSE_BINARY=/absolute/path/to/docker-compose python3 -m unittest discover -s tests -v
```

Python-зависимости не нужны: используется стандартная библиотека Python 3.10+.
Офлайн-тесты исполняют настоящий `main()` и все этапы установки, заменяя Docker
daemon, сетевые вызовы, изменение sysctl и подтверждение тестовыми реализациями.
Они проверяют порядок команд, сбои, продолжение, секреты и конфигурацию. Это
не тест работающих сервисов Pyrus. Подробности: [docs/TESTING.md](docs/TESTING.md).
